# Deploying ZentraGrid to Render

Step-by-step. Should take about 15 minutes.

---

## Before you start

You need these values ready (you already have them):

| Value | Where it came from |
|---|---|
| `TG_API_ID` | my.telegram.org |
| `TG_API_HASH` | my.telegram.org |
| `TG_SESSION` | `python scripts/generate_session.py` |
| `TG_OWNERS_CHANNEL` | `-100XXXXXXXXXX` (your real id — run `make channels`) |
| `TG_METADATA_CHANNEL` | `-100YYYYYYYYYY` |
| `TG_FILES_CHANNEL` | `-100ZZZZZZZZZZ` |
| `FIREBASE_PROJECT_ID` | `zentragrid` |
| `FIREBASE_CLIENT_EMAIL` | Firebase service account JSON |
| `FIREBASE_PRIVATE_KEY` | Firebase service account JSON |

> **Channel ids are placeholders here.** This README is public, so the real
> `-100...` ids are not written down. Get yours with `make channels` and put
> them straight into Render's environment variables.

> ⚠️ **Rotate your Telegram session before going live.** The session string you
> generated earlier was shared in a chat. Anyone holding it has full access to
> your Telegram account. Go to **Telegram → Settings → Devices → Terminate**
> that session, then run `python scripts/generate_session.py` again and use the
> new string in Render only.

## Step 1 — Firebase setup

You need **`FIREBASE_PROJECT_ID`** — that's it in the simplest case.

1. <https://console.firebase.google.com> → project **zentragrid**
2. **Authentication → Sign-in method → Google → Enable**
3. **Authentication → Settings → Authorized domains** → add your frontend domain

`FIREBASE_PROJECT_ID` is just `zentragrid`.

### Do I need a service account key?

**No.** Verifying a Firebase ID token only requires Google's *public* signing
keys, which the backend fetches and caches automatically. With just
`FIREBASE_PROJECT_ID` set, the app runs in **`jwks` mode** and validates the
signature, issuer, audience and expiry of every token.

If your Google Cloud organisation blocks key downloads you'll see:

> *Key creation is not allowed on this service account. Please check if service
> account key creation is restricted by organisation policies.*

That's the `iam.disableServiceAccountKeyCreation` org policy. **Just skip the
key** — leave `FIREBASE_CLIENT_EMAIL` and `FIREBASE_PRIVATE_KEY` unset and
deploy. Everything ZentraGrid does works in `jwks` mode.

### Optional: the full Admin SDK

Only needed if you later want to mint custom tokens, disable users from the
server, or revoke sessions mid-lifetime. To add it:

**Project settings → Service accounts → Generate new private key** → from the
downloaded JSON take `client_email` → `FIREBASE_CLIENT_EMAIL` and `private_key`
→ `FIREBASE_PRIVATE_KEY` (keep the `\n` escapes; the backend un-escapes them).

If the org policy blocks this, an admin can allow it at
<https://console.cloud.google.com/iam-admin/orgpolicies> → *Disable service
account key creation* → edit for your project. But again — you don't need it.

## Step 2 — Push to GitHub

```bash
cd zentragrid
git init
git add .
git commit -m "ZentraGrid backend"
git branch -M main
git remote add origin https://github.com/<you>/zentragrid.git
git push -u origin main
```

Confirm `.env` was **not** committed:

```bash
git ls-files | grep -c "^\.env$"     # must print 0
```

(`.gitignore` already excludes it, but check anyway.)

---

## Step 3 — Create the Render service

1. <https://dashboard.render.com> → **New → Blueprint**
2. Connect your GitHub repo → Render detects `render.yaml`
3. Click **Apply**

`render.yaml` already sets the build command, start command, health check path
and non-secret env vars. It creates a `starter` plan service in Singapore
(closest region to India — change `region:` if you prefer).

---

## Step 4 — Fill in the secrets

In the Render dashboard → your service → **Environment**, set every variable
marked `sync: false`:

```
TG_API_ID              37144075
TG_API_HASH            <your api hash>
TG_SESSION             <your NEW rotated session string>
TG_OWNERS_CHANNEL      -100XXXXXXXXXX
TG_METADATA_CHANNEL    -100YYYYYYYYYY
TG_FILES_CHANNEL       -100ZZZZZZZZZZ

FIREBASE_PROJECT_ID    zentragrid

# Optional - only for the full Admin SDK. Skip these if your org policy
# blocks service-account key creation; jwks mode needs neither.
# FIREBASE_CLIENT_EMAIL  firebase-adminsdk-xxx@zentragrid.iam.gserviceaccount.com
# FIREBASE_PRIVATE_KEY   -----BEGIN PRIVATE KEY-----\nMIIE...\n-----END PRIVATE KEY-----\n
```

`API_KEY_PEPPER` is auto-generated by Render — don't touch it.

Update `CORS_ORIGINS` to your real frontend domain:

```
CORS_ORIGINS   https://zentragrid.app,https://www.zentragrid.app
```

Click **Save Changes** — Render redeploys automatically.

## Step 5 — Verify

```bash
curl https://<your-service>.onrender.com/health
```

```json
{"status":"ok","service":"ZentraGrid","env":"production","storage_backend":"telegram"}
```

Then the deeper probe:

```bash
curl https://<your-service>.onrender.com/health/ready
```

```json
{"status":"ready",
 "storage":{"backend":"telegram","connected":true,"authorized":true},
 "auth_mode":"jwks",
 "auth_ready":true,
 "firebase_project_id":"zentragrid",
 "service_account_key":false}
```

`auth_mode` tells you which verification path is live:

| mode | meaning |
|---|---|
| `admin` | full Admin SDK (service-account key present) |
| `jwks` | keyless — verified against Google's public keys. **Perfectly fine.** |
| `insecure` | dev bypass. Must never appear in production (boot is blocked) |
| `unconfigured` | `FIREBASE_PROJECT_ID` missing — sign-in will fail |

If `connected: false` → the session string or channel ids are wrong.
If `auth_mode: unconfigured` → set `FIREBASE_PROJECT_ID`.

Check the Render logs for the startup line:

```
zentragrid startup env=production storage=telegram firebase_configured=True
zentragrid.telegram telegram_client_ready
zentragrid.repositories index_loaded type=owner count=N
```

## Important operational notes

**Keep `--workers 1`.** Each worker opens its own MTProto connection and holds
its own in-memory index. More workers = more Telegram connections from one
account (flood-ban risk) and a per-worker rate limiter. Scale with Render
*instances*, not workers, and add Redis for shared state when you do.

**Don't use the free plan.** Free instances sleep after inactivity. On wake the
MTProto session reconnects and all indexes re-scan the channels from scratch —
slow cold starts and unnecessary Telegram load.

**Startup cost grows with your data.** Index loading scans all three channels
once at boot. A few thousand records is fine (seconds). Past ~50k records,
consider snapshotting the index or moving metadata to Redis — the repository
abstraction is already built for that swap.

**Telegram flood limits are real.** Sustained heavy uploads will eventually hit
`FloodWaitError` on the account. For serious traffic, add a queue with retry
and back-off in front of the upload path.

**Render request timeout.** Very large downloads through the proxy can hit
platform limits. The `/stream` endpoint caps each range response at 16 MiB,
which keeps individual requests short — prefer it over `/download` for big
media in browsers.

## Production checklist

- [ ] Old Telegram session terminated, new one generated
- [ ] `.env` not in git (`git ls-files | grep .env`)
- [ ] `APP_ENV=production` (disables `/docs`, enables HSTS)
- [ ] `CORS_ORIGINS` set to real domains, no `*`
- [ ] `AUTH_ALLOW_INSECURE_TOKENS=false`
- [ ] `API_KEY_PEPPER` generated, stored somewhere safe (rotating it kills all API keys)
- [ ] Firebase Google Sign-In enabled
- [ ] `FIREBASE_PROJECT_ID` set (service-account key optional)
- [ ] Frontend domain added to Firebase **Authorized domains**
- [ ] `/health/ready` shows `connected: true` and `auth_mode: admin` or `jwks`
- [ ] Session account is admin (post/edit/delete) in all three channels

The app refuses to boot in production if insecure tokens are on, the pepper is
still the default, or CORS is wildcarded — so a misconfigured deploy fails loudly
instead of silently running insecure.
